# mongodb_agent_engine

Atlas Agent Engine deployment of the zero-copy RAG pipeline. Two tools, split
across two sub-agents: `knowledge-retriever` searches and returns pointers with
no text, `source-reader` resolves a pointer and returns verified bytes. All
retrieval, S3 and span-verification logic lives in `pipeline/`; this package only
registers tools, selects a model, and assembles the graph.

## Workspace layout

The **repository root is the agent workspace**, not `mongodb_agent_engine/`. Both tools
import `pipeline.retrieval` and `pipeline.spanio` directly, so `pipeline/` has to
be inside the built image, and the workspace is whichever directory holds
`agent.yaml`. Root it is. Run `agentengine init`, `agentengine build` and
`agentengine deploy` from the repository root.

Files that make the root a workspace:

| File | Purpose |
| --- | --- |
| `agent.yaml` | Name, entrypoint, feature flags, sandbox secret grants, egress allow-list |
| `dev.yaml` | Local `agentengine dev up` settings only. Never read by build or deploy |
| `uv.toml` | A fixed `exclude-newer` date. The scaffold writes `"7 days"`, which older uv releases cannot parse |
| `pyproject.toml` | Adds the SDK names to the existing pipeline dependencies. The base images supply the real packages |
| `.agentengineignore` | Narrows the source archive `agentengine build` uploads |
| `.env` | The only runtime secret source locally. Host environment variables are ignored inside the container |

`agentengine build` does not upload a directory, it uploads a source archive of
the whole workspace. With the root as the workspace that would mean shipping the
docs, the test suite and the seed corpus to the platform. `.agentengineignore`
denies every top-level entry (`/*`) and then names the ones that ship: the agent,
`pipeline/`, `infra/`, and the build inputs. That keeps about 450 KB of docs,
tests and seed documents out and ships about 125 KB.
`tests/test_packaging.py` fails if a later edit negates `docs/`, `seed/` or any
other withheld path back in, or if a package named for the wheel is not in the
archive, which would break the build rather than leak anything.

The first line is `/*` rather than `*` on purpose: gitignore syntax cannot
re-include a file whose parent directory is excluded, so excluding only the
top-level entries is what makes `!/pipeline/` work.

## SDK surface

Verified against two sources, in this order of authority:

1. A scaffold generated by `agentengine create --template hello-world-agent --llm anthropic`.
2. The SDK source as installed in the platform's base images:
   `agent-engine-sdk-langgraph` 0.0.96 in the hosted builder and 0.0.95 in the
   local dev image (CLI `0.1.107-alpha`). Neither installs the SDK from an index;
   both use wheels baked into the image, so `pyproject.toml` declares the names
   without pinning a source.

What the code uses:

```python
from agent_engine_sdk_langgraph import App
from deepagents import SubAgent

app = App(app_name="zero-copy-rag")

@app.tool(is_local=False)
def search_knowledge(query: str, k: int = 8) -> str: ...

@app.entrypoint
def build_agent():
    return app.deep_agent(llm=..., tools=[], subagents=[...], system_prompt=...)
```

Four details that are easy to get wrong:

- **Tools return `str`.** The platform hands the return value to the model as
  tool-message content. A `dict` or `list` return does not get serialized for
  you, so both tools wrap their result in `json.dumps`.
- **`is_local` defaults to `True`.** That is the opposite of what the published
  docs describe, and the default puts the tool in the agent runtime rather than
  the Tool Pod. Both tools pass `is_local=False` explicitly, and a test asserts
  it, because a silent revert would move S3 and MongoDB credentials into the
  process running the model loop.
- **`SubAgent` is a TypedDict, not a class,** and its required keys are `name`,
  `description` and `system_prompt`. There is no `instructions` key. Its `tools`
  field takes tool objects, not tool names, which is why `app.py` resolves them
  from `app.get_tools()` through `_tools_named`.
- **`deep_agent` wraps the model itself.** Pass the raw `BaseChatModel`, not
  `app.llm(...)`: deep_agent applies `SecureWrappedLLM` internally, and
  pre-wrapping registers the model twice under one id. Likewise leave
  `checkpointer` unset; its default sentinel resolves to `app.checkpointer()`.

### Where the published docs are stale

The platform documentation available while this agent was built disagreed with
the shipped scaffold in several places. The scaffold wins.

| Item | Docs say | Scaffold and SDK do |
| --- | --- | --- |
| Secret block | `required_secrets: {aer, tools.<name>}` | `sandboxes: {agent, tool}: {secrets, tools}` |
| Egress shape | `network.egress` plus `network.egress_mode` | `network.egress` as a list of `{fqdn, ports}`; no `egress_mode` is generated |
| Tool placement default | Remote (Tool Pod) | `is_local: bool = True`, so local unless overridden |
| LLM credential | One of `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `CEREBRAS_API_KEY` | A single generic `LLM_API_KEY`, with the provider chosen in Python |

`required_secrets` is the legacy shape. The SDK still parses it
(`RuntimeAgentConfig.required_secrets`), but nothing in the runtime packages
reads the parsed value, and its own model comments say "parsed for
compatibility; ignored at enforcement". Enforcement is server-side, from
`sandboxes`, which is what `agentengine agent validate` checks and what the
scaffold ships. `agent.yaml` here uses `sandboxes` only.

### Integration risk worth naming

**No shipped template uses `deep_agent`, `SubAgent`, or `deepagents`.** The
feature is real (`agent_engine_sdk_langgraph/deep_agent.py`, with its own tests
and a `deepagents==0.5.3` pin), and `features.deep_agent: true` is required, not
optional: the SDK's own config model says the flag "must be true for
`App.deep_agent()` to work". But this agent is on a path the templates do not
exercise, so it carries more first-deploy risk than the single-graph
`ToolNode` pattern every template uses.

That flag also costs something. It switches on the Tool Pod's built-in
filesystem and shell handlers (`filesystem_read`, `filesystem_write`,
`shell_execute` and the rest), which are off by default precisely so agents that
do not run deep agents do not carry that attack surface. This agent needs none
of them. It is surface accepted to get sub-agent delegation, and it is the
strongest argument for the fallback below. The fallback, if deep agents misbehave
on the platform, is to rebuild `build_agent()` as the standard
`StateGraph` + `ToolNode` loop and keep the retrieve-then-read discipline in the
system prompt alone. That loses nothing the platform was enforcing, for the
reason set out in the next section.

## What the capability split does and does not enforce

This is the design's central claim, and it is easy to overstate. Be precise.

**Enforced in this repo.** The `read_span` tool's signature accepts a `chunk_id`
and nothing else, and forwards it positionally. No caller, model or otherwise,
can supply a bucket, key, etag, byte range or content hash.
`tests/test_agent_wiring.py` pins both halves. Separately, `search_knowledge`
wraps `pipeline.retrieval.vector_search`, whose projection has no `text` field by
construction, so the retrieval path cannot return document text at all.

**Enforced by the platform.** Secrets are deny-by-default and granted per
sandbox. `agent.yaml` gives the agent sandbox nothing and grants MongoDB, Voyage,
the LLM key and the AWS credentials to the tool sandbox only. Egress is
deny-all by default and every destination is named. Both are server-side; neither
can be verified from the client source.

**Not enforced anywhere.** The sub-agent boundary. Nothing in the docs, the SDK,
or `deepagents` treats a sub-agent's `tools` list as a dispatch restriction; the
only platform validation applied to a sub-agent spec is rejecting string model
references. Both tools also share one Tool Pod, so they share one process and one
set of credentials. A subverted `knowledge-retriever` is constrained by the fact
that the retrieval tool cannot return text, not by the fact that it was not given
the reader.

So the split is a correctness and prompt-discipline mechanism, not an isolation
boundary. The isolation that exists comes from the tool signature, the projection,
and the sandbox secret grants.

## Configuration

`agent.yaml` grants these to the tool sandbox: `MONGODB_URI`, `VOYAGE_API_KEY`,
`LLM_API_KEY`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`. Everything else the
pipeline reads has a default in `pipeline/config.py`, including `AWS_REGION`
(`us-east-1`), `KNOWLEDGE_COLLECTION` (`knowledge_zc`) and `MONGODB_DB`
(`temporal`). `S3_BUCKET` is deliberately absent from the
grants: `read_span` takes the bucket and key from the pointer document, never
from configuration.

The corpus bucket is `s3://temporal-agentic` in `us-east-1`, and
`temporal-agentic.s3.us-east-1.amazonaws.com` is in the egress allow-list
alongside the regional endpoint. A different bucket needs its host added to
that list first (`docs/RUNBOOK.md` section 5).

Query embeddings go to MongoDB's hosted Voyage endpoint, `VOYAGE_BASE_URL`,
default `https://ai.mongodb.com/v1`. The voyageai SDK would otherwise pick the
endpoint from the shape of the credential: a key beginning `al-` routes to
`ai.mongodb.com`, anything else to `api.voyageai.com`. Inferring a network
destination from a credential prefix is a bad thing to have an egress allow-list
depend on, so `pipeline/clients.py` passes `base_url` explicitly.
`api.voyageai.com` is not in the allow-list, and `tests/test_egress.py` holds
the configured endpoint and the allow-list to each other.

Model selection lives in `mongodb_agent_engine/llm.py`, driven by `LLM_PROVIDER` with
an optional `LLM_MODEL` override. The platform's convention is that provider and
model stay out of `agent.yaml`.

Model calls go through the Grove gateway. `LLM_PROVIDER` defaults to
`grove-anthropic` (`claude-sonnet-5`); `grove-openai` is the other gateway
route, and `anthropic`, `openai` and `gemini` call the provider directly.
`LLM_API_KEY` holds the Grove API key under a `grove-*` provider. Grove
authenticates on an `api-key` header rather than the provider's own scheme, so
the model is built with `base_url` pointed at the gateway and that header set.
Grove's documentation packages this as `ChatGroveOpenAI` and `ChatGroveAnthropic`
subclasses; `llm.py` passes the same kwargs directly instead, which keeps the
provider imports inside the function where the test environment can do without
them.

`grove-gateway-prod.azure-api.net` is the only model host in the egress
allow-list. The direct provider hosts are deliberately absent, so switching
`LLM_PROVIDER` to `anthropic`, `openai` or `gemini` needs
`agentengine agent egress add <host>:443` first. Two tests in `tests/test_llm.py`
pin both halves of that: the gateway host must be in `agent.yaml`, and the three
direct hosts must not be.

One place Grove's documentation does not apply here. It says to pass the model
to `app.llm()`. That is right for a plain agent and wrong for this one, because
`deep_agent()` applies `SecureWrappedLLM` itself.

### Credential resolution timing

`pipeline/config.py` builds its `settings` singleton at import. In the Tool Pod
the tool module can be imported before the sandbox's secrets are in the
environment, which would freeze blank credentials into a process-wide client for
its whole life. `pipeline/clients.py` therefore resolves credentials on every
call, preferring the configured value and falling back to the live environment
when it is blank, and keys each client cache on the resolved value. Local
development and the test suite are unaffected, because there `settings` is always
populated and the fallback never fires.

## First-deployment checklist

All seven steps are done. The agent is deployed and has answered with correct
citations from the hosted Tool Pod. In order, from the repository root:

1. `agentengine init` and pick the org and project. It also writes its own
   `.agentengineignore` if one is missing; this repo already has one, so check that
   `agentengine init` left it alone.
2. Fill `.env`. It is created with every value blank, is git-ignored, and is
   stripped from the source archive unconditionally.
3. Set deployed secrets, which are separate from `.env` and never read from it:
   `agentengine secret set MONGODB_URI`, then `MONGODB_DB`, `VOYAGE_API_KEY`,
   `LLM_API_KEY` (the Grove key), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`.
   Run `agentengine secret sync` afterwards, or pass `--sync` to the last one.
   `agentengine deploy` also refuses to run until every populated `.env` key
   exists as a secret, config included; `grep` the keys into
   `agentengine secret set --from-file -` to import them without putting values
   on the command line. Existing as a secret is not the same as reaching the tools:
   the Tool Pod sees only what `sandboxes.tool.secrets` grants.
4. Add the Agent Engine data-plane IP ranges to the Atlas cluster's IP access
   list with `agentengine atlas setup-ip-access`. An access list opened to
   `0.0.0.0/0` for testing also unblocks the deploy, but it is wider than a
   production cluster should be. Remove it once the data-plane ranges are in.
5. Confirm the deployed AWS credentials can read `s3://temporal-agentic`. Its
   host is already in the egress allow-list.
6. `agentengine dev up` and exercise both tools in the Playground before deploying.
7. `agentengine build`, then `agentengine deploy`.

### What the local run actually showed

All four egress entries were exercised: `ai.mongodb.com` for embeddings,
`grove-gateway-prod.azure-api.net` for the model, and both S3 hosts for
`read_span`. The scoped `sandboxes.*.secrets` lists worked; the scaffold's
`["*"]` was not needed. `features.deep_agent: true` was honoured, and the Tool
Pod registered the two project tools alongside the eight deep-agent built-ins.

One finding is worth carrying into the deploy, because it is invisible until
egress is enforced. botocore resolves `us-east-1` alone to the global
`s3.amazonaws.com`, so a bucket there is addressed as
`<bucket>.s3.amazonaws.com`, which the allow-list does not name. The Tool Pod's
proxy answered CONNECT to that host with 403 and every `read_span` failed, with
botocore reporting only `Failed to connect to proxy URL`, which discards the
cause. `pipeline/clients.py` now pins `us_east_1_regional_endpoint: regional`;
`tests/test_egress.py` asserts on the host boto3 actually builds, since
comparing `agent.yaml` against `pipeline.config` never catches this. Every other
region is regional already, so the fix is a no-op outside `us-east-1`.

### What the first deploy showed

The hosted Tool Pod's proxy behaves like the dev-mode one. The first question
sent through `agentengine invoke` came back with verbatim quotes from chunks 38 and
40, and each quote was checked against `read_span` afterwards. That exercises
Atlas, Voyage, Grove and the regional S3 host from inside the deployed
boundary.

Two things the local stack hid, both caused by dev bind-mounting the repo:

- The SDK git pin. Dev installs baked wheels and skips the pinned names; the
  hosted builder resolved the pin, tried to clone the private repo, and failed.
- `MONGODB_DB`. `pipeline.config` reads `.env` from disk, so in dev the tools
  saw the real database name without it being granted. `.env` never ships, so
  hosted, they would have queried the default database and found nothing. It is
  now granted in `agent.yaml`, and `tests/test_packaging.py` pins the grant.

The hosted SDK is 0.0.96 and the dev image carries 0.0.95, under the same
package name. Earlier dev images baked an older SDK under a different import
name; that gap is closed, and `app.py` imports only `agent_engine_sdk_langgraph`.
